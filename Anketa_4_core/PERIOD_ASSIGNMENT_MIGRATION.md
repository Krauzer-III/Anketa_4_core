# Одно назначение периода на тестируемого — миграция и правила

## Новое поведение (вариант А)

У каждого тестируемого не более одной строки в `AccessForTestables`. При переходе
на другой `TestPeriod` система **обновляет `TestPeriodID` у той же строки**, а не
добавляет новый `AccessForTestable`.

**`AccessForTestable.ID` остаётся прежним.** Поэтому без изменений сохраняются:
первичные ответы 360°, мотивации, Кеттелла и компетенций; `TestResult.Results`;
`TestableUser.LK_Data`; связь с аккаунтом. В отчётах все эти результаты после
перевода относятся к **новому** периоду. История прежней принадлежности по
согласованному варианту А не сохраняется.

Повторное назначение того же периода ничего не добавляет и не активирует закрытое
назначение. Перевод **на другой** период активирует существующее назначение.
Создание одного тестируемого, CSV, регистрация нового тестируемого и
операции PeriodController используют одну бизнес-модель.

Сервис: `Services/PeriodAssignmentService.cs`. Для конкурирующих запросов
блокируется строка тестируемого (`SELECT ... FOR UPDATE`), а индекс
`IX_AccessForTestables_TestableID` является уникальным.

## Применение к существующей БД

**Перед миграцией создайте резервную копию обеих БД** (Anketa и Identity).
Новая миграция: `20261123000000_SinglePeriodPerTestable`.

1. Выявите прежние дубли:

```sql
SELECT "TestableID", COUNT(*) AS assignments,
       array_agg("ID" ORDER BY "ID") AS access_ids,
       array_agg("TestPeriodID" ORDER BY "ID") AS period_ids
FROM "AccessForTestables"
GROUP BY "TestableID"
HAVING COUNT(*) > 1;
```

2. Если запрос ничего не вернул, примените миграцию из каталога
`Anketa_4_core/Anketa_4_core`:

```bash
dotnet ef database update --context AnketaContext
```

3. Проверьте, что индекс уникальный, и нет повторов:

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE tablename = 'AccessForTestables'
  AND indexname = 'IX_AccessForTestables_TestableID';

SELECT "TestableID", COUNT(*) FROM "AccessForTestables"
GROUP BY "TestableID" HAVING COUNT(*) > 1;
```

**Если дубли уже существуют, миграция намеренно останавливается без удаления
записей.** У старых `AccessID` могут быть разные `TestResult`, ответы 360°,
мотивации, Кеттелла и компетенций. Автоматическое удаление лишних строк
каскадно уничтожило бы эти результаты. Простое изменение их внешних ключей
может также породить противоречивые повторные ответы или несколько `TestResult`
у одного назначения. Поэтому нельзя безопасно запускать `DELETE` или
`UPDATE` наугад.

Для таких экземпляров до миграции нужно провести отдельную **без потерь**
консолидацию: архивировать полные записи и JSON каждого `AccessID`,
разобрать конфликты первичных ответов и отчётных агрегатов, подтвердить
целевой `AccessID`, перенести все ссылки и проверить итоговый единый JSON.
Без этой проверки данные автоматически не объединяются. Ошибка миграции
является защитой от повреждения архива результатов, а не ошибкой БД.

**Важно:** приложение в `Program.cs` автоматически применяет миграции
Identity DB, но не Anketa DB. Поэтому применить эту миграцию вручную —
обязательный шаг развертывания на существующей базе.

## Регрессия

Автоматические тесты проверяют:

- один и тот же `AccessID` до и после переназначения;
- сохранение первичных данных всех типов тестов и `LK_Data`;
- повторное назначение того же периода без дублей;
- закрытое назначение и повторное назначение;
- перенос из карточки тестируемого и формы периода;
- создание одиночного тестируемого, CSV и регистрацию;
- ошибочные и неизвестные ID без частичных сохранений;
- одновременные операции в двух контекстах;
- уникальность на уровне PostgreSQL даже в обход сервиса;
- отказ от автоматического удаления старых дубликатов.

Команда: `dotnet test Anketa_4_core/Anketa_4_core.sln --configuration Release`.
