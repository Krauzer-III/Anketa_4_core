# План Unit-, интеграционного и ручного тестирования Anketa 4

Документ относится к ветке `lk-cabinet-fields` и тестовому ответвлению `qa/unit-and-scenarios`.
Цель — проверять не только штатные сценарии, но и границы, некорректные входные данные,
повторные запросы, конкурирующие изменения, изоляцию пользователей и целостность БД.

## 1. Как запускать автоматические тесты

Тесты используют настоящий PostgreSQL, поскольку приложение использует PostgreSQL-специфичные
блокировки `FOR UPDATE` и транзакции. Каждый тест создаёт отдельные временные базы для Anketa
и Identity и удаляет их после завершения.

Локальный запуск:

```bash
# PostgreSQL должен быть доступен на localhost:5432
export ANKETA_TEST_CONNECTION="Host=localhost;Port=5432;Database=postgres;Username=postgres;Password=postgres"
dotnet test Anketa_4_core/Anketa_4_core.sln --configuration Release
```

GitHub Actions запускает тот же набор автоматически на ветке `qa/unit-and-scenarios`.
Отчёт TRX сохраняется как артефакт workflow.

## 3. Подготовка тестовых данных

Создать тестовые учётные записи:

- `admin` — полный доступ к администрированию;
- `moderator` — управление тестируемыми, периодами, новостями и результатами;
- `verificator` — просмотр результатов и пакетные отчёты;
- `filial_user` — доступ к тестируемым своего филиала;
- `testable_user` — доступ только к собственному личному кабинету и назначенным тестам.

Создать два филиала, два периода (один активный, второй закрытый), два уровня резерва,
тестируемых с кодами `000101`, `000102`, `000103`. У одного тестируемого создать личный кабинет,
у второго оставить `LK_Data = null), у третьего сохранить повреждённый JSON.
Один пользователь филиала должен быть привязан к филиалу A, другой — к филиалу B.

Для тестов повторных отправок заранее подготовить результаты 360, мотивации, Кеттелла и компетенций
с разными `AccessForTestable.ID`, чтобы проверить, что данные разных периодов не смешиваются.

## 4. Авторизация и разграничение доступа

| ID | Действие | Ожидаемый результат |
|---|---|---|
| AUTH-01 | Открыть личный кабинет без входа | Перенаправление на вход / Challenge |
| AUTH-02 | Пользователь testable_user открывает чужой кабинет по подменённому ID | Доступ запрещён, чужие данные не возвращаются |
| AUTH-03 | filial_user открывает тестируемого своего филиала | Доступ разрешён |
| AUTH-04 | filial_user открывает тестируемого другого филиала | Forbid / ошибка доступа |
| AUTH-05 | verificator открывает список результатов | Доступ разрешён согласно роли |
| AUTH-06 | testable_user вызывает административные URL напрямую | Forbid |
| AUTH-07 | POST без antiforgery token | Запрос отклонён |
| AUTH-08 | Подменить AccessID в POST теста | Система сверяет AccessID с пользователем и последним периодом |
| AUTH-09 | Использовать старый AccessID после назначения нового периода | Старый период не принимается |
| AUTH-10 | Последний период закрыт, предыдущий активен | Предыдущий период не становится доступным |

### 5.1 Загрузка и отображение

| ID | Вариант | Ожидаемый результат |
|---|---|---|
| LK-01 | Новый кабинет с NULL в LK_Data | Возвращается объект с начальными значениями |
| LK-02 | В LK_Data сохранён корректный JSON | Отображаются сохранённые значения |
| LK-03 | В JSON отсутствуют отдельные секции | Секции отображаются пустыми / с предусмотренными дефолтами |
| LK-04 | В JSON присутствуют неизвестные root-поля | Они не теряются после загрузки и сохранения |
| LK-05 | В LK_Data массив или строка вместо корневого объекта | Контролируемая ошибка, не HTTP 500 с необработанным исключением |
| LK-06 | В LK_Data синтаксически неверный JSON | Контролируемая ошибка и запись в журнал |
| LK-07 | Логин не привязан к TestableUser | 404 / сообщение «Личный кабинет не найден» |
| LK-08 | TestableID не имеет TestableUser | 404 / сообщение об отсутствии кабинета |

### 5.2 Сохранение каждой секции

Проверить каждую секцию отдельно: открыть редактор, добавить одну запись, изменить её,
сохранить, обновить страницу и убедиться, что данные остались.

- LK-10 ProfTasks — 0, 1 и несколько профессиональных задач.
- LK-11 TrainingProgramms — мероприятие с датой, продолжительностью 0 и положительной продолжительностью.
- LK-12 DistanceLearning — выбор 0, 1, 2 и 8 курсов; проверка IsPlanned.
- LK-13 AdvancedTrainingCourses — пустые и заполненные сроки/результаты.
- LK-14 LanguageTrainings — пустой язык, заполненный язык, текущий и целевой уровень.
- LK-15 TeachingActivities — пустая запись, частичная запись, заполненная запись.
- LK-16 LK_ViceBoss — объект без задач, одна задача, несколько задач.
- LK-17 Internships — пустой список задач, один период, несколько периодов.
- LK-18 Mentorships — отсутствие наставничества и заполненная запись.
- LK-19 ReportBooks — 1 профессиональная книга и 2 книги по личностно-деловым компетенциям.
- LK-20 ProfessionalRetrainings — неполная и полная запись.
- LK-21 ProjectActivities — пустой проект, заполненный проект.
- LK-22 ConferencesAndCompetitions — разные типы событий.
- LK-23 PsychologicalConsultations — 0, отрицательная и положительная длительность.
- LK-24 DevelopmentalActionMaproperty — все вложенные таблицы, пустые и заполненные строки.
- LK-25 PersonnelMotivation — каждое поле по отдельности и весь объект целиком.

Для каждой секции дополнительно проверить:
- сохранить пустой массив / пустой объект;
- передать объект вместо массива и наоборот;
- передать строку, число, null и неверный тип поля;
- добавить неизвестное поле;
- отправить секцию с отсутствующими необязательными полями;
- отправить большой объём текста;
- дважды нажать «Сохранить»;
- открыть две вкладки и одновременно сохранить разные секции;
- обновить страницу сразу после сохранения;
- прервать соединение во время POST.

Ожидается: одна секция заменяется атомарно, другие секции и неизвестные root-поля сохраняются,
повторная отправка не создаёт дубли, ошибки возвращаются в понятном виде.

### 5.3 Интерфейс личного кабинета

- LK-30 Проверить обычный режим и compact-режим.
- LK-31 Проверить добавление и удаление строк в каждом списке.
- LK-32 Удалить первую, последнюю и единственную строку.
- LK-33 Проверить автоматическую нумерацию строк после удаления.

- LK-36 Проверить checkbox и select, сохранение и повторное открытие.
- LK-37 Проверить XSS-строки в текстовых полях: содержимое должно отображаться как текст, а не исполняться.

## 9. Психологическое тестирование Кеттелла

- KET-01: тестируемый не привязан к аккаунту — ошибка.
- KET-02: нет активного последнего периода — ошибка.
- KET-03: возраст отсутствует, 0, отрицательный, очень большой — проверить валидацию.
- KET-04: пол не выбран или передано неизвестное значение — ошибка.
- KET-05: вопросы не загружены — понятное сообщение.
- KET-06: для вопроса нет вариантов ответов — понятное сообщение.
- KET-07: передан ID ответа от другого вопроса — ответ не сохраняется.
- KET-08: передан ID несуществующего ответа — ответ не сохраняется.
- KET-09: корректный ответ — сохраняется ровно один ответ.
- KET-10: повторно отправить ответ на старый вопрос — дубль не создаётся.
- KET-11: открыть две вкладки и отправить разные ответы на один вопрос — засчитывается только один актуальный ответ.
- KET-12: ответить на все вопросы — рассчитываются категории и нормативные баллы.
- KET-13: отсутствует ключ для выбранного ответа — транзакция откатывает последний ответ и JSON.
- KET-14: отсутствует таблица нормирования — пользователь получает ошибку, результат не объявляется завершённым.
- KET-15: все ответы есть, но итоговые категории отсутствуют — Finish не сообщает об успешном завершении.
- KET-16: проверить повторное открытие завершённого теста — повторное прохождение запрещено.

## 10. Компетенции — первый и второй год

Каждый год тестируется независимо, при одинаковом QuestionNumber в двух годах должны использоваться разные QuestionID.

- COMP-01: открыть год 1 и год 2 отдельно.
- COMP-02: год обучения 1/2 определяет стартовый год личного кабинета.
- COMP-03: передать year=0, 3, отрицательное число — 404.
- COMP-04: нет вопросов выбранного года — контролируемая ошибка.
- COMP-05: у ситуации 3 варианта ответа — ошибка конфигурации.
- COMP-06: у ситуации 5 вариантов ответа — ошибка конфигурации.
- COMP-07: отправить 3 приоритета — ошибка.
- COMP-08: отправить 5 приоритетов — ошибка.
- COMP-09: повторить приоритет 1 дважды — ошибка.
- COMP-10: передать приоритет 0 или 5 — ошибка.
- COMP-11: подменить ID одного из вариантов — ошибка.
- COMP-12: отправить QuestionID от другой ситуации — старый ответ не сохраняется.
- COMP-13: повторная отправка уже сохранённой ситуации — дубликат не создаётся.
- COMP-14: частично сохранённая старая ситуация — новый полный набор заменяет старый.
- COMP-15: завершить последнюю ситуацию года 1 — рассчитывается только год 1.
- COMP-16: завершить год 2 — применяется шкала нормирования второго года 0–2, 3–5, 6–8, 9–10, 11, 12.
- COMP-17: завершить год 1, затем год 2 — результат первого года не меняется.
- COMP-18: попытаться открыть завершённый год повторно — запрещено.
- COMP-19: открыть старую вкладку после назначения нового периода — отправка блокируется.
- COMP-20: удалить результаты одного года — другой год остаётся неизменным.

## 19. Известные незавершённые места и дефекты, которые нужно подтвердить тестами

1. `TestableController.Create(MVC_TestableEditFull)` сейчас возвращает Redirect, но фактически не создаёт тестируемого.
2. `GenerateReportPdf`, `GenerateReportXlsx` и `SaveLKData` сейчас являются заглушками и возвращают NoContent.
3. `ReportController` ищет шаблон в `ContentRoot/Reports/report.xlsx`. В репозитории есть README с требованием положить туда отдельный бинарный шаблон; файл `wwwroot/reports/report.xlsx` не является автоматической заменой этого файла.
4. `JSON_ResultModel(string)` перехватывает исключение и оставляет свойства null; вызывающий код может получить NullReferenceException позднее.
5. `JSON_Motivation_Result(MotivationTest)` обращается к ряду строковых полей через Contains без гарантии, что поле не null.
6. CSV-парсеры используют разбиение строки по символу-разделителю; кавычки и разделитель внутри значения могут обрабатываться некорректно.
7. `PeriodController.Edit` строит Dictionary из переданных BoundTestables; дубли TestableID могут вызвать исключение.
8. Методы заполнения справочников необходимо проверить на идемпотентность — повторный запуск не должен создавать дубли.
9. Для первого года компетенций нормализованные уровни пока не рассчитываются: в JSON LevelNumber остаётся null. Нельзя считать это корректным завершённым функционалом без согласования шкалы.
10. Для мотивационного теста проверить обязательность RecomendPosition и Recomendator именно на сервере, а не только через атрибуты модели.
11. Контроллер 360° не содержит серверной проверки диапазона q01–q15: автоматический тест подтверждает, что отрицательное и завышенное значение сохраняется. Это дефект валидации, а не допустимое поведение.

### Исправления, внесённые в тестовой ветке

- Исправлены шесть предикатов в `LKPeriodRatingService`, из-за которых проект не компилировался (результат `Filled` типа int использовался как bool).
- Исправлен вложенный Razor-блок в `Views/Result/GetMotivationTest.cshtml`.
- При создании нового `TestableUser` в регистрации и импорте теперь задаётся начальный JSON `{}`; ранее в NOT NULL поле `LK_Data` записывался null, что приводило к ошибке PostgreSQL.
- В `TestableController.UpsertAccessForTestable` добавлена загрузка навигации `TestPeriod`; без Include редактирование назначения периода падало с NullReferenceException.

## 20. Критерии приёмки

- Все автоматические тесты, не помеченные Skip, проходят.
- Все пропущенные тесты имеют понятную причину и отдельную задачу на исправление.
- Нет необработанных исключений при неверном вводе.
- Любая операция изменения данных либо сохраняется целиком, либо откатывается целиком.
- Данные разных пользователей и периодов не смешиваются.
- Пользователь не может изменять или просматривать чужие данные через подмену ID.
- Каждая ошибка в интерфейсе понятна пользователю, а технические детали записываются в журнал.
- Все незавершённые функции явно обозначены как незавершённые, а не считаются пройденными.
